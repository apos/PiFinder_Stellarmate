Quick Links

Direct links to things you'd otherwise have to look up: PiFinder's own remote page (its web UI), the INDI/mount setup wizard running on PiFinder itself, this Control Center's own address (useful if you're bookmarking it or opening it on another device), and the project's documentation on GitHub. The status line at the top reflects whether PiFinder's web server is answering at all - it can say "running" even if a piece of hardware (camera, IMU, GPS) is missing, since that's a separate check (see Mode & Power below).

Quick keys, next to the OLED mirror, drive PiFinder's own on-screen menu without switching to its separate Remote page. Three layouts, switched top-right and remembered per browser: A (a D-pad cross), B (a 2x4 grid) - both send the same Left/Up/Down/Right/Enter/Long presses PiFinder's Remote page does - and C, which isn't a keypad at all but one button per PiFinder found on the network (labeled by its last two IP octets), opening that PiFinder's full Remote page directly for whenever the compact keypad isn't enough. A keypad briefly dims after each press while it's in flight - PiFinder's own web server only handles one request at a time, so rapid clicks queue up rather than getting lost.

Mode & Power

Four collapsible groups: simulation/testing tools, a deeper hardware check, optional extra-hardware bridges, and service/power actions - each covers one part of running and exercising PiFinder on this device.

Simulation and testing

Four independent, combinable levels, each replacing a different piece of the real pipeline while everything else stays real - useful for testing this Control Center, the Mount Bridge, or PiFinder itself without needing working (or any) physical hardware.

Whole device: Real Mode / Fake Mode - Real Mode uses the actual PiFinder hardware (camera, IMU, GPS). Fake Mode runs a completely separate, headless instance with everything simulated.

Solve Simulation (PiFinder built-in) is PiFinder's own "Tools -> Test Mode" feature - it substitutes canned test images for the camera so plate-solving can be exercised without sky access, while the IMU/keypad/GPS stay live. This is not the same thing as Fake Mode above (which runs a whole separate instance with no hardware at all).

Injected Solve (Dead Reckoning) manually sets PiFinder's reported position to a chosen RA/Dec (via /api/fake_solve), then lets PiFinder's normal IMU dead-reckoning track from there exactly as it would from a real solve - useful for testing anything downstream of a solve (e.g. the Mount Bridge) without sky access or even a working camera. Only visible in this row while active; there's no "enable" control here since it needs a target position, currently only set via the API used for testing. It does not just drift forever once armed: while active, PiFinder watches the IMU's angular rate to tell "being moved by hand" apart from "settled" - the moment real motion stops, the current dead-reckoned estimate is treated as a fresh solve and re-anchored, exactly mirroring what happens for real once a user stops panning and the solver catches up on the next frame. So error only accumulates during motion, not while stationary - but that re-anchor trusts PiFinder's own estimate at settle time, with nothing independent to check it against. If the device's actual physical pointing has drifted from that estimate, this will happily confirm the wrong position as truth. Good for exercising downstream logic (Mount Bridge, UI, ...) with zero hardware, not for verifying dead-reckoning accuracy itself - see Mount is source below for that.

Keep fresh (next to Injected Solve's Toggle) re-injects that same position every few seconds instead of just once - a testing aid specifically for Verify/Alert and the two Auto-correct presets, which only act on a solve within Mount Bridge's SolveFreshnessMaxAgeNP window (default 5s - see #79 in the CHANGELOG for why that gate exists). Without a real mount or sky continuously refreshing PiFinder's position, a one-time Injected Solve goes stale within seconds and permanently blocks Auto-correct from ever firing - indistinguishable, from the GUI, from Auto-correct simply not working. With Keep fresh running, PiFinder holds a fixed "ground truth" position indefinitely; intentionally desyncing a mount from it (GoTo it elsewhere, switch its own tracking off, ...) and watching Auto-correct pull the mount back is what actually exercises the mechanism a real misconfigured/mistracking mount would need it for - the mount drifts, PiFinder stays right, Auto-correct corrects the mount. This is the opposite situation from Mount is source above, where PiFinder is the one following the mount; Keep fresh is for testing the direction where PiFinder is supposed to correct the mount instead. Turns itself off automatically when Injected Solve does.

Mount is source (Mount Bridge) reverses every other Coupling mode's direction: instead of PiFinder's solve driving the mount, the mount's own position (a real mount, or the stock INDI Telescope Simulator) is pushed to PiFinder through the exact same /api/fake_solve mechanism as Injected Solve above. Unlike a plain Injected Solve seed, each mount push is an independent ground-truth re-anchor, not PiFinder trusting its own settled estimate. This is a Mount Bridge Coupling preset (see the Mount Bridge Coupling section's Simulation group - like Verify/Alert or Auto-correct there), not an on/off toggle - turn it back off via the Mount Bridge tile's Decouple button, and it needs a mount connected in Mount Bridge (real or the Telescope Simulator) to enable at all.

Dead reckoning is a navigation technique going back centuries (sailing, aviation): starting from a last known, verified position, you estimate the current position by applying the motion measured since then - with no new external fix. PiFinder's version anchors on the last real plate-solve, then uses the IMU's measured rotation since that anchor to compute the current pointing. It's real sensor math on real physical motion, not a simulation of movement - which is exactly what Injected Solve and Mount is source above build on: they only substitute the anchor (a chosen position, or the mount's live position, instead of a camera solve), while the dead-reckoning that tracks movement in between anchors is the same real mechanism PiFinder always uses between solves.

Hardware test and details

Test Hardware runs a deeper functional check against each subsystem (an actual camera capture, an actual IMU read, PiFinder's own GPS status) and classifies any failure as a hardware problem, a driver problem, or a Python error - not just "is it plugged in." Runs automatically once when this Control Center starts, and again any time you click the button. Output also appears in the Terminal on the left. The Camera/Solve/IMU/GPS rows below it show the live result.

Optional external hardware

The two rows here (External SPI LCD, External numpad bridge) only matter if you've attached that specific extra hardware - leave them off otherwise. The Keyboard row is informational only (it needs physical key presses while PiFinder is stopped, so it can't be tested from here - use the shown command instead).

Service and power actions

PiFinder: Start / Stop / Restart control pifinder.service directly, independent of the Real/Fake Mode switch above - useful for a plain service bounce (e.g. after a config change) without switching modes.

This Pi: Reboot Pi / Shutdown Pi affect the whole Raspberry Pi, not just PiFinder or this page.

Install or Update

Only shown when an existing PiFinder installation is found at ~/PiFinder.

  • Install from: which branch of this project's own scripts/patches (not PiFinder itself) gets used the moment you click Reinstall or Update below - main (stable) by default for a fresh install, dev (beta) or any other branch by explicit choice. An existing install's Reinstall/Update defaults to (and stays on) whichever branch is already checked out, so a deliberate earlier switch carries forward instead of quietly reverting. The small "disk is currently on ..." note only appears if your pick differs from what's actually on disk right now (e.g. changed via a different terminal/tab since this page loaded) - click the ↻ button to double-check before starting a run.
  • Reinstall from scratch: deletes that directory entirely and clones a fresh copy from the official release branch, then re-applies all StellarMate patches. Use this if the installation seems broken, or you just want a clean slate.
  • Update: resets the existing directory to the official release branch (git reset --hard + pull) and re-applies all patches, discarding any local changes there. Keeps the directory, just brings the code up to date.
  • Reset: briefly stops pifinder.service/pifinder_splash.service/pifinder-setup.service (so they're not running against a half-deleted venv), then wipes ~/PiFinder's own Python virtual environment and build state. It does not disable or remove those services, and never touches INDI drivers, udev rules, or anything outside ~/PiFinder - your data, config, and installed services/drivers stay intact, just stopped until you re-run the setup script (or reboot). Use this to get a clean slate for a fresh setup run without losing anything else. See Uninstall below for the separate, much more thorough action that also removes this whole checkout.
  • Run Again (shown after a run finishes): resets this page back to the choice buttons above, without shutting anything down - use this if there's another install/update to do next. This webserver is meant to just keep running; restart it via PiFinder's own "Start Setup Wizard" button on the PFSM page if it's ever off, and stop it deliberately via launch_setup_gui.sh --shutdown-webserver from a terminal if you actually want to.

INDI-only

For running just the INDI drivers and Control Center on a host with no PiFinder hardware attached at all - e.g. a separate StellarMate/Astroberry "control host" coupled to a real PiFinder elsewhere over the network (see docs/concepts/remote_indi_coupling_split_host.md). Check the box, then click Install INDI-only.

Installs the INDI build dependencies (cmake, build tools, libindi-dev, git) and builds/installs both INDI drivers - nothing else. Your existing ~/PiFinder installation (if any) is never touched: no clone/patch, no Python environment, no star catalog, no GPIO/udev setup. On StellarMate, package installation briefly and automatically disables StellarMate's own Atomic Updates protection (voids the warranty while running) and restores it immediately afterward, success or failure - you'll see StellarMate's own warning text scroll past in the log; that's expected, not an error.

Uninstall

In its own PiFinder Stellarmate group, separate from Reinstall/Update/Reset above because it acts on much more: uses bin/uninstall_pifinder_stellarmate.sh --selfmove to stop and remove everything this project installed - systemd services, INDI drivers, the ~/PiFinder directory, and this ~/PiFinder_Stellarmate checkout itself. This page (and this whole Control Center) stops working once it starts, since the Control Center's own service is one of the things removed. Cannot be undone from here.

Device roles: All-in-one, PiFinder host, Control host

What is this about?

The Mount Bridge tile's role cards (inside "Setup checklist & diagnostics") cover three setup variants for integrating your PiFinder with INDI:

  • All-in-one: PiFinder hardware with mount - this one device does everything. The classic setup; if you only have one device, this is yours.
  • PiFinder host: PiFinder only, no mount - this device just shares its solved sky position on the network. The mount coupling happens on a separate control host.
  • Control host: no PiFinder hardware - this device runs the Mount Bridge and your mount, and couples to a PiFinder on another device. See the INDI-only section above for installing just what a control host needs.

A device by itself has no fixed role - the profile defines it. Clicking a card configures the selected profile for that role (which drivers it contains); the colored "Role:" line near the top of the tile always shows what the selected profile currently makes this device do. Switching roles is just a click - nothing needs reinstalling, and two full PiFinders can swap roles freely between sessions.

The split roles use INDI's native "remote driver" mechanism: the PiFinder host exposes its PiFinder LX200 driver on the network, the control host connects to it. No extra software on either side.

Split setup, step by step - on the PiFinder device

  1. Pick your Web Manager profile in step 1 and click the PiFinder host card. Confirm - PiFinder LX200 stays in the profile, Mount Bridge is removed.
  2. Converting a profile that used to be All-in-one? Remove any leftover mount driver (e.g. LX200 OnStep) from it via Web Manager or the StellarMate App - the mount belongs to the control host now, and a mount driver here would just fail to find its hardware. The role cards deliberately never touch drivers other than the two PiFinder ones, so this one step stays manual. The same applies to KStars' own Equipment Profile on this device, if you use Ekos here: it may still expect the mount and log "Failed to connect to LX200 OnStep" - either remove the mount there too, or simply don't start Ekos on this device at all (the PiFinder host role doesn't need it; KStars/Ekos belongs on the control host).
  3. Start the profile (step 1's Start button) if it isn't running.
  4. Note the green "This device's IP" shown under the cards - the control host asks for exactly this address. If several IPs are shown, use the one in the same network as the control host.

Mount, Ekos, Connect, and the Coupling presets disappear in this role - there is no mount here, so none of that applies.

Split setup, step by step - on the control host

  1. Pick (or create) the profile that contains your mount driver, then click the Control host card.
  2. Enter the PiFinder device's IP address when asked (the one from the other device's "This device's IP" line; port defaults to 7624).
  3. That's it - PiFinder LX200 (remote) + Mount Bridge are now in the profile. Continue with steps 4-6 (Mount, Ekos, Connect) and the Coupling presets exactly as in any local setup.

Good to know

  • The role cards and the step-3 driver buttons change the same profile - the cards are just the "do the right combination in one click" shortcut. Every change is visible in the tile's log, and a running profile is restarted automatically to apply it.
  • A device without PiFinder software installed (INDI-only) can never be All-in-one or PiFinder host - those two cards are disabled there, with the reason shown on hover.
  • Both devices must be on the same network, and port 7624 must be reachable between them (firewall).
  • Manual alternative to the Control host card: enter PiFinder LX200@<ip>:7624 in the profile's "Remote Drivers" field in Web Manager's own editor - same result.
  • Full architecture: docs/concepts/remote_indi_coupling_split_host.md in the project repository.

Mount Bridge

Couples PiFinder's own solved sky position with a real telescope mount, via the PiFinder Mount Bridge INDI driver - so you don't need to open the separate INDI Control Panel for the common cases. The tile is organized as a numbered setup checklist (below the divider line) plus a live status/operate area (above it): connection diagram, Coupling presets, and the drift readout.

Each numbered step shows a green checkmark once it's actually satisfied, and a yellow spinning symbol while its own action is running.

1. Profile

Pick the Web Manager Equipment Profile you want to use. "Simulators" is intentionally not selectable here - it's a read-only default meant for testing, not for a real setup. Create your own profile first, in Web Manager or the StellarMate App, if none exists yet. The Start/Stop button next to it starts or stops that profile's indiserver instance - it turns green while the profile is actually running.

2. KStars Link

Checks whether the matching Equipment Profile in KStars itself has "INDI Web Manager" enabled and pointed at this same Web Manager (the checkbox you'd see in KStars' own Profile Editor). This is read from KStars' own local database - never written, since KStars may have that file open at the same time, and you might deliberately want a different setup there. If it shows a warning, follow the steps shown (open KStars' Profile Editor, tick the box, save) and click Recheck.

3. Drivers

Adds or removes exactly two drivers in the profile: PiFinder LX200 (reports PiFinder's solved position as a telescope) and PiFinder Mount Bridge (does the actual coupling). Nothing else in the profile is touched. If the profile is currently running, adding or removing a driver here automatically stops and restarts it for you - indiserver only reads a profile's driver list once, at startup, so a restart is unavoidable for the change to actually take effect.

These buttons give fine-grained control over the individual drivers; the role cards above them do the same changes as one-click combinations - for most users, the cards are the easier way. Note that "PiFinder LX200: add" always adds the local driver (this device's own PiFinder); a remote PiFinder is set via the Control host card. When a remote entry is set, this button shows "PiFinder LX200 (remote <ip>): remove". Whatever you change, the "Role:" line near the top of the tile reflects the effect immediately.

4. Mount

Pick which other driver already in the profile is your actual mount, then click Link Mount - this is the one step that needs your judgment, since there's no reliable way to auto-detect "which driver is a telescope." Once linked, the button turns green and becomes Unlink Mount.

This step does not connect to your mount's own hardware (serial port, baud rate, etc.) - that's assumed to already be configured and working, either from a previous session or via the INDI Control Panel. Mount Bridge only needs to know which loaded driver is the mount.

5. Ekos

Steps 1-3 above all happen on the INDI Web Manager's own webpage - starting/stopping the profile, its driver list. Steps 4 and 6 replace what you'd otherwise do in KStars itself (its Profile Editor, or the INDI Control Panel usually opened from inside Ekos). This step is the other KStars-side fact worth knowing: whether Ekos itself has connected to this same profile - checked via a read-only D-Bus query to KStars, independent of whether steps 1-4/6 are all green. Since Ekos connecting to the specific PiFinder LX200/Mount Bridge/mount devices set up above is only possible if it's using this same profile, this step names it directly rather than hedging - if it says connected, it's this profile.

Hidden entirely if KStars isn't running at all - some setups drive everything from the StellarMate App directly and never open KStars, so there's nothing useful to say in that case.

6. Connect

Connects (or disconnects) each device's own CONNECTION property. Connect all (available) connects everything that's ready and not yet connected in one click - it turns green and becomes Disconnect all once everything is already connected. "PiFinder LX200" is a special case: it's automatically pointed at PiFinder's own internal position server (127.0.0.1:4030, fixed on every install) before connecting, since left on its default it would otherwise try to use a serial port - which is what your real mount's own driver usually needs instead.

Coupling & Autoconnect

Four one-click presets, applied to the Mount Bridge driver:

  • Verify/Alert only: watches the drift between PiFinder's solved position and the mount's reported position. Never moves the mount - just a passive "is my mount still aligned?" check.
  • Auto-correct (Sync): same watching, but corrects the mount by syncing it to PiFinder's solved position once drift exceeds the Threshold - an instant position update, no slewing, works on any mount.
  • Auto-correct (Goto & Track): same watching, but corrects by slewing the mount to PiFinder's solved position once drift exceeds the Threshold - actually moves the mount, needs a Goto-capable mount.
  • Goto-Forward: forwards every Goto command sent to PiFinder straight through to the real mount too, keeping them moving together. Threshold doesn't decide whether a Goto happens (every new PiFinder target is forwarded regardless) - but it does decide whether the arrival needs refining: once the mount finishes slewing, PiFinder's next solve is checked against it, and if still outside Threshold, the mount is synced (correcting its model) and sent the Goto again, repeating a few times before giving up if it still won't settle within Threshold.

The active mode is highlighted green.

Visual group

Verify/Alert only and Auto-correct (Sync) never slew the mount - a Sync is an instant position update, not a physical move - so both work on any mount, Goto-capable or not. This matches two of this project's original use cases: astrophotography's passive "is my mount still correctly aligned?" sanity check (Verify/Alert), and a manual push-to-then-correct workflow where you slew by hand until PiFinder shows on-target, and Auto-correct (Sync) straightens out whatever drift results afterward.

GoTo group

Auto-correct (Goto & Track) and Goto-Forward both physically slew the mount, so both need a real Goto-capable mount. Auto-correct (Goto & Track) continuously corrects existing drift by slewing to it; Goto-Forward matches this project's standalone-visual-use case instead - PiFinder becomes the single GoTo interface, and every new PiFinder target is forwarded regardless of Threshold, though Threshold still governs whether the arrival needs refining afterward (see above).

Setup: runs steps 1-4/6 above in one click (start profile, add drivers, connect - pausing for you to link your mount, the one step it can't decide for you) without applying any Coupling preset at the end. Use this to get everything ready first, then pick a mode deliberately once it's all connected.

Autoconnect: clicking any preset before steps 1-6 are actually finished doesn't just fail - it runs the exact same setup as the Setup button above automatically, then applies the coupling mode you originally clicked once it's done. The Setup button exists so you're not only discovering this by clicking a preset and seeing setup start unexpectedly.

Manual: Sync mount from PiFinder: a one-shot action, works regardless of which Coupling preset (or none) is active. Syncs the mount to PiFinder's current solved position right now - no Goto, no drift comparison, just an instant correction. Useful specifically after moving the mount by hand: none of the Coupling presets react to that on their own (Auto-correct only reacts on its next poll if drift already exceeds Threshold, Goto-Forward only reacts to a new PiFinder target, not a mount move).

Simulation group

The Mount is source control - and its full explanation - lives in the "PiFinder Mode, Test and Power" tile's Simulation and testing section, alongside Injected Solve, not here. It's still a Mount Bridge Coupling preset internally (same enable/active-state wiring as Verify/Alert, Auto-correct, and Goto-Forward), which is why it's documented as one of the Coupling groups in this list - just not shown as a row in this tile.

Drift readout

The large number top-right of the tile is the current angular drift between PiFinder's solved position and the mount's reported position, in arcminutes:

  • Green: within the Threshold you've set.
  • Yellow: past the Threshold.
  • Red: past roughly 0.5° (about the diameter of a full moon) - a generic placeholder for "probably out of your eyepiece's field of view," not a measurement of your actual eyepiece/camera.

Only shown while coupling is actively watching drift (Verify/Alert or Auto-correct) and connected - hidden otherwise.
